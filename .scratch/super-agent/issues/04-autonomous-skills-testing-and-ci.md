## Answer

### 交棒后各 Skill 交付什么

| Skill | 输入、职责与交付物 |
| --- | --- |
| `to-spec` | 读取入口已确认的目标和约束，产出用户可观察的验收条件、测试的公开接口及范围外事项。技术上的测试边界由规划会话确定，不再逐项找人确认；不能凭空补全产品意图。 |
| `to-tickets` | 把规格按可验证切片拆票；涉及前后端协同的功能必须前后端分离：**后端 + 接口契约文档票先行**，前端页面票通过 `Blocked by` 显式依赖对应后端票，并分别标注 `backend` / `frontend` 执行标签。每票指向对应验收条件，中枢核对拆分与依赖，程序检查引用与环路后才允许派工。 |
| `implement` / `tdd` | 每张实现票在独立 Worktree 工作。行为变更优先在规格约定的公开接口上做一轮失败测试、最小实现、重跑；读取相关模块文档，交付改动、验证结果与文档影响判定。 |
| `code-review` | `implement` 内并行启动两个独立审查会话：一路核对项目规范，一路核对规格与票据验收。两路看同一基线和候选提交，分别报告结论；缺规格、缺一路结论或仍有阻塞性问题时不能通过。 |
| `retro` | 依据执行证据提出环境改进。影响本票正确性、安全或现行质量标准的事项关票前修复；纯可选优化独立进入持续演进待办。修复改变了已审查行为时，重验受影响的测试和审查结论。复盘过程不写入仓库文档。 |

插件需提供三项专用 Skill（设计名）：`doc-tree` 按[文档树协议](./02-ai-doc-tree-protocol.md)定位与更新叶子；`test-scope` 识别仓库已有的测试入口，并为改动选择验证范围；`delivery-check` 汇集与候选版本匹配的验收、双路审查、测试、文档和合入证据。它们指导 Worker 做事，不替代程序的关票检查。最终复盘和依赖释放顺序见[中枢调度与上下文控制](./03-hub-agent-dag-and-context-control.md)。

### 测试在哪一步跑

- **开发循环**：跑当前行为的测试。修改一个模块，先跑该模块；改变对外契约，要把依赖该契约的模块纳入范围。没有针对性入口时，先补可验证的入口，或运行能覆盖它的现有套件，不能把“没有跑”报成通过。
- **单票合入**：验证本次改动和受影响的依赖，保留仓库已有的必需 CI 检查。结果须指明候选版本、实际跑了哪些检查、选择依据及结果。凡是修改公共基础设施或无法可靠界定影响范围，直接升级为全量回归。
- **集成／发布**：在实际集成版本上完成整套回归。同一集成版本、测试配置与相关环境已有可信结果时直接引用，不让每个 Worker 再跑一遍；换了合入基线或修复改变受测行为后，不沿用已失效的结果。

### 谁可以改规则

Worker 可在票据授权范围内改进项目检查、测试和导航，改动仍须接受独立审查。涉及跨票共享的 Skills、用户/团队自定义 Skills 或全局规则时，由独立维护任务或配置入口验证并审查新版本；当前任务继续使用启动时绑定的规则版本，不悄悄热换。任何任务都不能通过删除失败检查、降低验收要求、扩大权限或提高额度来让自己过关。资源与并发限制读取宿主的实际生效配置，不写死在 Skill 中。

### CI / CD 与完成条件

- 首期使用 GitHub Actions，Jenkins 预留同一结果接口：关联票据或计划、候选提交／集成版本、必需检查、运行结果和产物引用。中枢只消费摘要和证据链接；必需检查失败、取消、未运行或仍在等待时，不关票、不释放后继。
- 单票按验收和合入证据关票。计划收尾验证合入后的整体行为，并交付与项目匹配的产物，如可安装的软件包、可运行程序或预览环境。**合入不等于发布**。
- 生产环境只有在入口授权明确指定目标环境和发布范围、所需凭据可用时才可自动变更；有凭据不构成授权。没有生产授权时停在已验证产物。若上线是已承诺的交付条件，则以该产物在指定环境的发布及验证结果为准；失败可报告“已合入，未上线”，不能报告计划交付完成。
