# 15: 完成两次 retro 并重新取得失效证据

**执行角色：** backend

**What to build:** 在同一候选上经历双审后的 retro、验收与最终 retro，拿到供程序检验的 delivery-check 证据包，而不是一句「可以关票」。

**Blocked by:** [05 从 GitHub Actions 取得指定版本的检查证据](05-actions-evidence.md)；[10 在 implement 内并行取得两份独立审查结论](10-dual-review.md)

**Status:** ready-for-agent

**GitHub 实施票：** [#16](https://github.com/linxiovo/deepseek-harness-dev-hub/issues/16)

**对应规格：** [S10](../spec.md#s10)、[S13](../spec.md#s13)

**依赖理由：** 10 给出候选的两份独立审查及文档/选测记录；05 给出必需 CI 对应版本的真实结果。二者齐备才能演示可以排队与必须退回两种结果。

## 验收条件

- [ ] 从双审候选开始，以执行证据做第一次 retro 并修复；按规格/票验收检查后再做最终 retro 与必要修复。从票详情能看到顺序、对应版本与仍缺的检查。
- [ ] 最终 retro 发现一项会改变已审行为的问题，原有受影响的审查、验收、测试和文档结论失效；在新候选补齐重验后才得到可排队结果，不强制重跑无关部分。正确性、安全或现行标准问题不得延期。
- [ ] 纯可选改进成为独立持续演进待办，不算作本票未满足的验收；Doc Tree 仅保留仍有效的规则或导航，没有历史复盘叙事。
- [ ] delivery-check 汇集可打开的候选/基线、验收逐项结果、双审、实际测试/必需 CI、文档与修复证据；此时主干证据若未取得即标待合入，既不能自签正式交付也不释放后继。
