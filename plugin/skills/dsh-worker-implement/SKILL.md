---
name: dsh-worker-implement
description: Implement an authorized coding ticket in its verified worktree and collect reproducible candidate test evidence.
---

1. Read the ticket, its acceptance criteria and the repository guidance. Read `ticket/<id>` with `orchestrator_read` to confirm the worktree and pinned base. Use that worktree for edits and checks.
2. Load `dsh-worker-test-scope` to find the public verification entry and pre-merge coverage. For each behavior change, load `dsh-worker-tdd` and complete one red–green cycle before starting the next.
3. At the first runnable slice, finish the slice and commit it, then read the actual pinned base and candidate as full lowercase SHAs. In that same review round, dispatch two independent `code-review` subagents at once: one on `standards`, with repository guidance/Doc Tree sources, and one on `spec`, with the ticket/specification and acceptance sources. Give both the identical base/candidate pair, require each to load `dsh-worker-code-review`, and let each submit its own conclusion through `orchestrator_review_submit`. Start both in the same parallel delegation even if one must wait; never write either review conclusion yourself.
4. Wait for both submissions and inspect the review resource's aggregate state. A missing lane, blocked conclusion, or base/candidate mismatch is not approval: fix the findings, commit the fix, pin the new pair and rerun both independent reviews. Do not continue as ready while either lane is absent or blocked.
5. Finish all writes and review the complete diff. Commit the clean candidate and run the selected checks on it. Then pin the actual full lowercase base and candidate SHAs and dispatch both independent code-review subagents in the same parallel round, again with the same version pair and the separate standards sources and ticket/spec sources. Each reviewer reads `git diff <base>...<candidate>` and the commit list and submits its own evidence. The implementer must not author two summaries or substitute self-review for either lane.
6. Wait for both submissions and check the review resource's aggregate state. Any missing, blocked, or version-mismatched review means the candidate is not ready; repair and run both reviews again against the new candidate. Report ready only when both reviews pass for the same pinned pair and the selected checks, red–green evidence, and declared scope are complete, including actual consumers when their contracts changed.
7. Call `orchestrator_test_evidence` with the full candidate SHA, scope and reason, and each check's directory, exact command, status and observed output. Pass each observed red revision with its command, directory and failing assertion. Use `[]` when a required red is missing and `null` for a change with no red required. Retain the result, prerequisites and log or Session references in the `orchestrator_report` summary and PR when one exists.
8. On resumption, check the actual worktree, HEAD, base and run records. Never reuse review text from a prior or interrupted candidate: if either revision changed, re-pin the actual pair, re-evaluate scope and start both independent reviews anew for the current candidate. Reuse a red result only when its exact revision still reproduces the same assertion failure and the candidate contains the same regression check. Report unknown results as unverified.
9. Carry the ticket through self-review, commit, push and PR creation within its authorization. Follow required CI and human review, fix actionable failures and deliver the PR.
