---
name: dsh-worker-implement
description: Implement or resume an authorized coding ticket through candidate checks, dual review, retro, acceptance, and delivery-check.
---

1. Read the Ticket, its specification and repository guidance. Use `orchestrator_read` on `ticket/<id>` to confirm the verified worktree, pinned base and any Plan association. For a Plan Ticket, read `ticket/<id>/delivery-check` for the canonical criteria and evidence timeline. On restart, reconcile the available evidence with the live worktree, writer generation, clean HEAD and any PR head. An old HEAD or stale read cannot carry a pass for an affected or uncertain check; reacquire missing or invalid evidence. Wait for clarification only if the available sources cannot settle a contract question that materially changes required behavior; route just that question through the Hub and continue work it does not block.
2. Load `dsh-worker-test-scope` to locate the public verification entry, actual consumers and required checks. For each changed behavior, use `dsh-worker-tdd` to complete a red–green cycle before starting the next. Load `dsh-superagent-doc-tree` to update affected facts and contracts in the same candidate or establish why they remain unchanged.
3. At the first runnable slice, commit it and run **dual review**. Read `ticket/<id>/reviews` for the pinned `base` and live writer `generation`; pin the actual full lowercase candidate SHA. In one parallel delegation start two independent `code-review` subagents. Give `standards` the repository guidance and Doc Tree sources; give `spec` the ticket, specification and applicable acceptance criteria. The exact first-message marker is `DSH_REVIEW_ASSIGNMENT: {"axis":"standards|spec","base":"<base>","candidate":"<candidate>","generation":<generation>}`, with the assigned axis and actual values. Each child loads `dsh-worker-code-review`, inspects the pair and submits its own conclusion. Start both even if one must wait. Read the aggregate after both submissions: only a matching pass on both axes for the live pair and generation clears review. Repair blockers and dispatch both again; never author either conclusion.
4. Finish writes, inspect the complete diff and commit the candidate. On that clean SHA, run the selected checks covering actual consumers. Call `orchestrator_test_evidence` with the candidate, scope, reason and each check's directory, exact command, status and observation. Record the red revision, command, directory and observed assertion failure; use `[]` for required but missing red evidence and `null` when red is not required. Call `orchestrator_doc_impact` for the committed candidate and inspect its result. Record actual observations and give each tool an openable log or Session reference in `reference`. Keep prerequisites and references in `orchestrator_report` and the PR if one exists. Repeat **dual review** on this complete candidate. When required CI needs a remote candidate, push and open or update the authorized PR in time to start CI; don't wait for retro to start it.

For a Ticket not associated with a registered Plan, verify its own acceptance criteria, keep the normal `orchestrator_report` and authorized PR handoff, and follow required CI and human review for the exact PR head. Steps 5–8 apply to registered Plan Tickets. A missing or unreadable immutable Plan or specification for a Plan Ticket is an evidence gap, not permission to use the non-Plan path. Do not invent canonical criterion IDs or claim `ready_to_queue` outside delivery-check.

5. After matching **dual review**, examine the execution and review evidence for the **first retro**. Call `orchestrator_retro_evidence` with `{candidate, kind: 'first-retro', findings}`. Use `{id, category, summary, evidence, affects?}` per finding, with stable IDs and `category` of `correctness`, `security`, `standard`, or `optional`. Cite observed facts. For mandatory findings, list affected evidence keys (`tests`, `docs`, `acceptance:<id>`); omit `affects` if impact cannot be bounded, which invalidates all. A defect, security problem or current quality-standard violation is mandatory even if another check passed. Route pure optional improvements through the Hub as independently addressable backlog in `orchestrator_report`, using the finding ID and reference. Keep only current facts in Doc Tree.
6. **Repair** every mandatory finding before continuing. Commit the fixes and record `{candidate, kind: 'repair', fixes: [{id, evidence}]}` on the clean new SHA, citing how each was resolved. For a failed acceptance check, use its criterion ID as the fix ID. Compare the old and new pairs; identify the invalidated and unaffected evidence keys, their original observations and why any claimed unaffected result still applies. Treat uncertain impact as affected. Repeat affected local and Doc Tree checks, then dispatch fresh **dual review** of the new candidate with the repair diff and scope judgment. Each reviewer independently examines the proposed reuse on their axis and submits the exact accepted keys in `reuses`. Carry a passing result only if both current reviewers name it and delivery-check recognizes it; reacquire the rest. Prior approvals cannot consent for either reviewer.
7. Check the canonical criteria after matching dual review and a valid first retro. Call `orchestrator_retro_evidence` with `{candidate, kind: 'acceptance', results: [{id, status, evidence}]}` using registered IDs and `passed`, `failed` or `not_run`. Cite observations and logs; mark unobserved checks `not_run`. After repair, record at least one fresh acceptance result; a prior result covers only an explicitly reaffirmed key. Repair failures and supply missing checks before the **final retro**. Examine the accepted candidate and record `{candidate, kind: 'final-retro', findings}`. Use `findings: []` for either retro with no findings. If final retro requires repair, renew the review, acceptance and final retro on the new SHA. Follow the live timeline for any gate that must be completed again.
8. Ensure the authorized PR carries the current candidate; track actual required CI and human review for its exact head separately from local results. Read `ticket/<id>/delivery-check` for the evidence, status and missing gates. Failed, cancelled, pending, missing or wrong-version required CI is not a pass. On `return_for_recheck`, address the missing gates; report `ready_to_queue` only when the live package says so. Mainline verification is still `pending_merge`. The package does not authorize release, ticket closure, formal delivery or successor dispatch.
